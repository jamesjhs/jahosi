01 · Start here

What you are studying

Life Runner is the title inside public/labyrinth/labyrinth.html; Labyrinth is its portfolio name and URL namespace. This tutorial concerns that browser game. The separate LabyrinthApp portfolio entry describes an Android project and is not the implementation in this folder.

The player explores a generated maze from eye level, uses temporary hints, and tries to reach an exit. Practice removes score pressure; Timed Run adds countdowns and lives; High Score rewards speed without a countdown. The core design problem is orientation under uncertainty: a simple maze graph becomes challenging when the player can see only one corridor at a time.

JavaScript, not Java. No Java source, JVM, Java applet or Java build system is used here. JavaScript runs in the browser and Node.js. The two languages share some punctuation, but have different type systems, libraries and execution environments. A Java comparison appears below to help transfer programming knowledge accurately.

Learning goals

  • Trace an action from a DOM event through game state to a rendered frame.
  • Explain why depth-first generation and breadth-first routing solve different problems.
  • Distinguish geometry, materials, lights, shaders, fog and decorative glow.
  • Calculate movement, timer allowances, scores and rendering costs.
  • Review the implementation critically, with reproducible evidence.

Descriptions marked implemented refer to inspected code. Examples marked teaching example simplify it. Items marked proposed are exercises or improvements, not features already present.

02 · Tools

Run and inspect it

You need a browser with developer tools and a text editor. Node.js and npm run the existing portfolio server. In a checkout of the repository, install the package dependencies and use its start script:

npm install
npm start
# Visit http://localhost:3000/labyrinth/labyrinth.html
# Tutorial: http://localhost:3000/labyrinth/tutorial.html

The root server requires the contact and Turnstile environment settings listed in .env.example and README.md. Configure those locally before starting; do not put credentials in HTML. If the server exits with “Missing required environment variables”, that is portfolio configuration, not a graphics fault.

For front-end study alone, serve public with a local static HTTP server. The game can use local scores and its Canvas fallback without the score API. Opening via file:// changes origin and fetch/storage behaviour, so it is a poor way to reproduce hosted behaviour. Static hosting does not provide the Express API.

  1. Play a Practice level. Locate the preview, HUD, compass, hint and summary.
  2. Open DevTools → Network. Reload and identify the version request, attempted engine URLs, and score requests.
  3. Open Sources and search for boot, CFG, generateMaze and tick.
  4. Inspect Application/Storage for life_runner_progress_v1 and life_runner_scores_v1. Use a test browser profile before clearing them.
  5. Use responsive device emulation to inspect the layout; test real touch hardware for final control judgement.
Checkpoint: Explain why a page can render and accept movement even if /api/labyrinth/scores fails.
Answer

Maze rules and rendering live in the page. Fetch errors are caught and local storage supplies a fallback scoreboard; the API is an enhancement rather than the simulation engine.

Single-file packaging has a precise meaning

The game’s HTML, CSS, rules, fallback renderer and UI are in one document. The preferred 3D engine remains an external dependency. The loader first tries ./assets/vendor/three.min.js, then cdnjs, then jsDelivr. The inspected folder contains only the game HTML before this tutorial is added; the local vendor file is absent. A normal load therefore attempts a missing local file before using a CDN.

There are no downloaded character models, image texture packs, sound files or external physics engine in this game. The geometry and glow texture are generated in code. There is no service-worker registration or manifest here, so comments about “PWA-friendly” loading do not establish an installed offline PWA.

The portfolio information page separately uses Tailwind’s CDN and a Google font. This tutorial embeds its own CSS, diagram and optional calculator script; it needs no CDN, font, image or library to read offline.

04 · Presentation

HTML, CSS and interface layers

The document places #sceneHost behind the interface. JavaScript inserts either the WebGL canvas or a 2D canvas there. Other elements sit above it: a loader, menu, score screen, level preview, transitions, HUD, compass, actions and touch controls. The maze is drawn in a canvas; buttons remain ordinary HTML controls.

05 · Read the code

JavaScript methods and symbols

The large game script is enclosed by (function () { ... })();, an immediately invoked function expression (IIFE). It creates a private scope, avoiding a global variable for every piece of game state. The early version-check script is another private scope; it deliberately shares one promise via window.__labyrinthVersionRefreshPromise.

Collections, callbacks and closures

An Array stores cells, routes and scores. A Set avoids duplicate wall keys or repeated BFS visits. A Map links each reached cell to its predecessor. Object.create(null) makes a keyboard dictionary without inherited keys such as constructor. JSON serializes data as text; it cannot preserve a function or a live Three.js mesh.

bindJoystick is a higher-order function: a callback tells it where to send normalized input. Its inner event handlers form closures over activeId and the touch origin. Each joystick therefore keeps its own active finger without creating a custom class.

// Teaching example: data → transformation → result
const topTen = scores
  .map(item => ({ name: String(item.name), score: Number(item.score) || 0 }))
  .sort((a, b) => b.score - a.score)
  .slice(0, 10);

map creates a transformed array; sort mutates that new array; slice selects a portion without mutating it. Read chained calls left to right. Distinguish slice from splice, which removes or replaces items in the original array.

Bridge from Java

// JavaScript teaching example
const cell = { walls: { n: true, e: true, s: true, w: true } };

JavaScript’s Number generally represents double-precision values; Java separates int, float and double. A browser promise is not a Java thread: await resumes a continuation after the awaited result becomes available.

06 · Follow the flow

Architecture and state

The code separates configuration (CFG), cached DOM references, renderer objects, run state, maze data, player state and input intent. These are logically separated inside one closure, rather than split into modules. This makes the document portable, while increasing the number of dependencies each function can reach.

Version check→Quality profile→Load Three.js or fallback→Bind controls→Menu→tick()

States and transitions

boot → menu → preview → playing → gameover → menu
                            │       ↑
                            ├ timeout → retry same maze
                            └ clear → continue → next level → preview

gameState holds boot, menu, preview, playing or gameover. isLevelTransition and isTimeoutTransition add substates while gameState remains playing. applyUIState() derives which panels should appear from state; updateHUD() copies numbers and mode labels to the screen.

A transition waits for a promise whose resolver is saved in a variable. A button click invokes that resolver. This gives readable sequential code—show explanation, wait, prepare next level—without a blocking loop. Guards after each await check that the player has not left the run.

escapeToMenuAndScores() resolves pending waiters before ending the run, so an async flow is not left waiting forever. A larger game could use a state machine with explicit transition events or a run generation ID to prevent an old asynchronous operation affecting a newer run.

Trace one action: Hint click → guard in setupInput → activateHint → decrement hint count and calculate BFS route → save expiry time → next tick updates floor/minimap feedback. The click does not render a new maze or directly move the player.
07 · Algorithms

Procedural maze generation

A maze is an N × N array of cells, indexed grid[y][x]. Each cell begins sealed with north, east, south and west walls. Openings must be reciprocal: removing east from one cell also removes west from its neighbour. This invariant makes movement, rendering and pathfinding agree.

// Actual cell structure before the carving pass
{ visited: false, walls: { n: true, e: true, s: true, w: true } }

// Teaching example of a reciprocal passage
grid[y][x].walls.e = false;
grid[y][x + 1].walls.w = false;

Step 1: randomized iterative depth-first search

  1. Create all cells and mark the centre visited.
  2. Push its coordinates onto a stack.
  3. Inspect the stack’s last cell and gather unvisited orthogonal neighbours.
  4. If any exist, randomly select one, open both sides of the connecting wall, mark it visited and push it.
  5. If none exist, pop the stack to backtrack.
  6. Repeat until the stack is empty, then remove the temporary visited properties.

This first pass forms a spanning tree: every cell is reachable and there is one simple path between any pair. The stack avoids a deeply recursive function consuming the JavaScript call stack. Random neighbour choice favours the long winding passages typical of depth-first mazes; it does not sample every possible maze with equal probability.

Step 2: introduce loops

The code collects closed internal east/south walls, then removes up to floor(N² × 0.055) of them. Looking east and south avoids counting each wall twice. At size 5 this requests one extra opening; at size 9 it requests four. A loop adds alternate routes to a connected maze; it does not create a disconnected region. “Extra openings” are a count based on cell area, not a 5.5% independent chance for every wall.

Step 3: place exit and player

Choose a random boundary exit excluding corners and open its outward wall. Reflect the exit coordinates across the maze centre to get an opposite point. Place the player about 67% of the way from centre toward that point, clamped to the interior. The carving seed and player start are different concepts. Random spawn yaw prevents the initial camera direction revealing the exit direction.

Math.random() provides variety without a stored seed. Reproducing a particular maze is therefore difficult. Proposed: inject a seeded generator, record its seed and rules version, and use the same seed for regression tests and shareable challenges.

Reason before coding: Why can removing more walls never disconnect this maze?
Answer

Removing a wall adds a graph edge. Existing paths remain available, so connectivity cannot decrease. Adding a wall would require a new connectivity check.

08 · Routing

Pathfinding and hints

shortestPath() runs breadth-first search (BFS). It uses a queue, a visited set and a predecessor map. Each cell is a graph node; an open wall is an edge of equal cost. BFS examines routes in increasing number of edges, so the first arrival at the exit is shortest in cell steps.

// Teaching example: efficient queue traversal for a future refactor
const queue = [[startX, startY]];
let head = 0;
while (head < queue.length) {
  const [x, y] = queue[head++];
  // For each open, in-bounds, unseen neighbour:
  // mark seen, record predecessor, then queue.push(neighbour).
}

The current implementation instead uses q.shift(). That is concise but repeatedly removes from the front of an array. A head index avoids repeated front-removal work. Once the destination is found, the predecessor links reconstruct a reversed route, then reverse() puts it in start-to-exit order.

A path contains both endpoints. Thus a path of 13 cells represents 12 inter-cell moves. Returning [] indicates no route. BFS is shortest for equal costs; if you add mud, slopes or turn penalties, use a cost-aware search such as Dijkstra’s algorithm or A* with a justified heuristic.

How hints reuse the solution

activateHint() calculates a route from the current player cell, spends one hint, stores the full route for the minimap, and stores up to eight route cells for world highlighting. The five-second duration is an absolute performance.now() deadline. Eight cells include the current cell, so the segment shows at most seven onward cell transitions.

updateHintVisuals() changes floor colours and emissive values while active, then restores the saved base values. drawMazeMap() is shared between preview and hint map, preventing two competing map implementations. The preview hides the player direction; the hint map includes it.

The full-map route is more generous than the short world segment. This is an important design choice: a hint helps next-step navigation in first person, but also briefly reveals the complete route to a player who can read the overhead map.

09 · Spatial maths

Coordinates and camera maths

Maze data uses integer (x,y) cells. The world uses continuous (x,z) floor coordinates; world y is height. Cell centres are four world units apart and the maze is centred around the origin.

centre = (mazeSize - 1) / 2
worldX = (cellX - centre) × 4
worldZ = (cellY - centre) × 4

cellX = round(worldX / 4 + centre)
cellY = round(worldZ / 4 + centre)

For a 5 × 5 maze, cell (2,2) maps to world (0,0); cell (4,0) maps to (8,-8). worldToCell() clamps the result to the grid. That prevents invalid indexing, but also means it cannot independently prove that a point is outside the physical maze.

At yaw zero, forward movement follows negative Z. Facing direction is (-sin(yaw), -cos(yaw)). The implementation multiplies its positive sine/cosine vector by a negative forward input, producing that result. Positive yaw turns toward west. Radians satisfy π = 180°; π/2 is a quarter turn.

The camera uses Euler order YXZ: yaw, pitch, then roll. Eye height is 1.35; wall height is 2.4. The perspective camera has a 72° vertical field of view, near plane 0.05 and far plane 380. Horizontal field of view varies with aspect ratio. Near/far distances affect clipping and depth precision, not movement rules.

10 · Graphics

The Three.js rendering pipeline

initThree() creates a WebGLRenderer, Scene and PerspectiveCamera. buildWorld() converts the maze data into meshes beneath a per-level Group. A group is a transform/ownership hierarchy, not a guarantee that its children render in one draw call.

Maze cells→Geometry + material→Meshes in scene→Camera transforms→GPU shaders→Canvas pixels

Geometry and scene construction

Floors are thin boxes sized 4 × 0.08 × 4. Walls use two box orientations with 0.28 thickness and 2.4 height. The longer wall dimension includes thickness so joins overlap rather than leave visible cracks. Shared floor/wall geometry reduces geometry allocation, while a Set of wall keys prevents placing one shared wall twice.

Each floor tile receives a cloned material so hints can recolour one tile without affecting all tiles. Cell coordinates and original colours live in mesh userData. The renderer’s objects are therefore a presentation of the graph; they are not the authoritative collision model.

A cylinder and torus mark the exit. A box, torus, glow sprite and point light mark the start. A distant sphere, halo sprite and directional light establish the sun. Hint beams use transparent cone meshes and sprites. These are generated primitives, not imported art assets.

From triangles to pixels

Three.js submits mesh buffers and shader programs to WebGL. Vertex processing transforms triangle vertices from model space to world, camera and clip space. Rasterization determines covered fragments. Fragment shading combines material properties, lighting and fog into colour; depth testing determines which visible surface wins. The browser composites the canvas with the HTML overlays.

The package does not author custom GLSL vertex or fragment shaders. Its material choices select Three.js shader implementations. Knowing shader stages is still valuable: changing a light is a lighting input; changing a box is geometry; changing the camera modifies projection.

Resizing updates camera aspect, projection matrix, renderer size and pixel ratio. CSS canvas size and drawing-buffer resolution are distinct: a 1000 × 600 CSS canvas at ratio 2 has about 2.4 million buffer pixels, four times the ratio-1 pixel count.

11 · Look development

Lighting, shading and glow

Lighting describes light sources. Shading describes how a surface responds to them. Glow here is largely a deliberate visual construction. Keeping these separate prevents the common mistake of expecting a bright-looking object to illuminate everything around it.

Standard materials

Floor and wall materials use MeshStandardMaterial, Three.js’s metallic/roughness physically based shading model. The floor uses metalness 0.25 and roughness 0.5; walls use 0.25 and 0.45. A higher roughness spreads reflections, while higher metalness changes the balance of diffuse and specular response. These are artistic values; the package does not measure a real material or load an environment map.

// Excerpt from the wall material
new THREE.MeshStandardMaterial({
  color: new THREE.Color().setHSL(levelHue01() + 0.05, 0.58, 0.23),
  emissive: new THREE.Color().setHSL(levelHue01() + 0.05, 0.62, 0.12),
  metalness: 0.25,
  roughness: 0.45
});

color provides base colour. emissive contributes self-lit appearance. Emissive colour does not automatically cast light onto neighbouring meshes; explicit point lights supply that visible lighting. MeshBasicMaterial, used for the sun and beams, is unlit, so its colour remains visible without standard lighting response.

Palette and spatial readability

levelHue01() advances hue by 0.11 per level and wraps it. HSL separates hue from saturation/lightness, making a family of palettes easy to generate. Each floor’s ring index is max(abs(x-centre), abs(y-centre)): a square-ring distance, not Euclidean distance. Interpolating inner/outer colours makes outer floor tiles brighter, offering a subtle location cue.

How the glow is built

getHintGlowTexture() draws a radial gradient to a canvas and wraps it in a CanvasTexture, cached for reuse. A sprite is a camera-facing textured quad. Layering wide transparent sprites with narrow cone meshes creates a bright beam impression at modest geometric cost.

AdditiveBlending adds light-like colour to the existing image. transparent: true enables transparency handling; opacity controls visibility. Beam materials disable depth writing, reducing unwanted transparent depth occlusion, while depth testing still matters. DoubleSide makes the open cones visible from inside and outside. Overlapping transparent layers can become expensive because the same pixel is shaded repeatedly.

Sine waves animate intensity, scale and opacity; for example 0.5 + 0.5 * sin(t) oscillates between zero and one. This is a periodic pulse, not random flicker. Ring rotation currently increments per frame, a separate timing issue discussed later.

Shadows and bloom: the code does not enable shadow maps, assign mesh shadow flags, or run a bloom/postprocessing pass. Soft halos are sprites and additive geometry; wall shading is not a cast shadow. Adding shadow maps would require shadow-enabled lights, receivers/casters and a performance budget.

Version-specific colour output

The game assigns renderer.outputColorSpace = THREE.SRGBColorSpace, but its remote libraries are r128. That release uses outputEncoding, so this assignment does not configure r128’s intended output conversion. This is a source compatibility issue, not a reason to copy newer documentation blindly. For an r128-specific correction, investigate renderer.outputEncoding = THREE.sRGBEncoding; a modern upgrade requires a broader colour-management review. See the pinned r128 renderer source.

Experiment in a local copy: Set wall emissive colour to black, keep lights unchanged, and compare corridor readability. Then remove the purple fill light. Record which change alters self-lit surfaces and which alters illumination. This teaches causal control of the look.
12 · A second renderer

Canvas raycasting fallback

If engine loading or initialization throws, boot() creates a Canvas 2D renderer. It reads the same maze and player data and presents a simpler first-person view. This is a useful example of separating simulation from display, though the fallback does not achieve full feature parity.

One frame, step by step

  1. Paint sky and floor gradients, using the level hue.
  2. Project a south-facing sun cue when it falls within the view angle.
  3. For each screen column (or pair of columns on lower-end devices), calculate a ray angle across a 0.62π horizontal field of view, about 111.6°.
  4. Advance that ray in world-space steps of 0.14 or 0.22 units. On a cell change, ask whether the connecting wall is open.
  5. Convert the first hit distance into a vertical wall strip.
  6. Shade by distance and an approximate side factor. Add a floor tint during hints.
// Equations used by the fallback
correctedDistance = hitDistance × cos(rayAngle - playerYaw)
wallPixelHeight = min(0.95 × canvasHeight,
                      WALL_HEIGHT × canvasHeight / correctedDistance)
shade = clamp(1 - correctedDistance / maxDistance, 0.08, 1)
sideMultiplier = hitSide ? 0.85 : 1

Cosine correction reduces fisheye distortion by using distance perpendicular to the view plane. The wall-height expression is a simple projection approximation; it does not reproduce the Three.js camera exactly. Side shading is a heuristic, not a surface-normal lighting calculation. The renderer is a stepped grid raycaster, not physically based ray tracing.

The background is not textured floor casting: gradients are enough to imply depth cheaply. The fallback ignores camera pitch and uses a different field of view, so it will feel different from WebGL. Its hint floor wash is not the 3D route-cell highlight; the Canvas minimap still carries the route.

Resilience needs deliberate testing

Use DevTools request blocking to block both Three.js CDN patterns, then reload and confirm the local vendor path also fails. Re-enable requests after the test. A throttled request that never completes is different from a failed request: the script loader has load/error handlers but no explicit timeout.

Mouse-look, pointer-lock and resize listeners are installed inside initThree(), not in the fallback initializer. Keyboard arrows strafe rather than turn. As written, desktop ray mode therefore lacks the normal mouse turning path; touch look is wired separately. A failed WebGL initialization can also leave partially created objects/canvas behind. These are concrete parity/cleanup tasks for a future revision.

Proposed optimization: Replace small-distance stepping with grid DDA, which jumps directly to the next vertical or horizontal cell boundary. First preserve ray hit tests and wall-side results. Compare time spent rendering the same seeded maze, rather than assuming the new algorithm is faster everywhere.
13 · Game feel

Input, movement and collision

Event handlers record intent; updatePlayer(dt) turns that intent into motion once per frame. WASD and arrow keys supply forward/back/strafe values. The mouse changes yaw/pitch while pointer lock is active. Touch movement and look joysticks supply continuous values from -1 to 1. H activates a hint; Escape ends the current run or returns to menu/scores.

Pointer Lock delivers relative mouse movement without stopping at the screen edge. The implementation requests it on appropriate clicks, exits it for overlays, and attempts recovery after focus returns. Browsers control whether a request is accepted; a click remains the dependable recovery action. MDN’s Pointer Lock guide explains the event and activation model.

Normalize, smooth, integrate

Combined input is normalized if its length exceeds one. Without this, pressing forward and right yields magnitude √2, giving an unfair diagonal speed boost. Small analogue input remains small rather than being forced to full speed.

// Teaching example of the movement sequence
const magnitude = Math.hypot(ix, iy);
if (magnitude > 1) { ix /= magnitude; iy /= magnitude; }
const alpha = 1 - Math.exp(-acceleration * dt);
velocity = lerp(velocity, targetVelocity, alpha);
position += velocity * dt;

lerp(a,b,t) means a + (b-a)t. Exponential alpha gives a similar response over elapsed time at different frame rates. Movement speed is 5.2 units/second; acceleration response is 12.5 and deceleration response 10.5. These are smoothing-rate parameters, not a full mass/force physics simulation. Fast deceleration feels precise; slow deceleration feels slippery.

Touch look has its own smoothing and sensitivity. Pitch is limited to 0.47π on desktop and π/6 for coarse pointers. The narrower mobile range reduces accidental vertical drift. An invert toggle changes the touch vertical-look sign.

Touch identity and cancellation

bindJoystick() tracks a finger by its touch identifier. The initial touch defines the origin; the stick is clamped to a radius of 48 pixels and normalized. touchend and touchcancel reset only the joystick owning that finger. This prevents one lifted finger from cancelling the other joystick and prevents stuck motion after cancellation.

Collision without a physics engine

tryMoveAxis() moves X first, then Z. Each axis may stay in the same cell or cross one open neighbour. Axis separation permits sliding along a wall during diagonal motion. applyWallCollisionBuffer() keeps the camera 0.38 units away from present wall boundaries, approximating a small player body.

Maximum nominal travel in one clamped frame is 5.2 × 0.05 = 0.26 units, much smaller than the four-unit cell. This supports the adjacent-cell test. Raising speed or the timestep cap substantially could invalidate that assumption; collision design must be revisited with movement tuning.

The outer world clamp and exit test do not currently agree. The intended design is to cross the outward edge of the exit cell, but the code tests every open side and clamps the player short of the outward threshold. The source review gives the arithmetic and a focused debugging exercise.

14 · Time

Time and the animation loop

tick() measures time, advances eligible game rules, updates feedback, renders once and requests another frame. requestAnimationFrame aligns work with the browser’s animation schedule; it is not a promise of 60 FPS. Background tabs commonly pause or reduce callbacks. See MDN’s animation-frame reference.

  1. Check that the chosen renderer is initialized.
  2. Read clock delta and clamp it to at most 0.05 seconds.
  3. If playing outside transitions, decrease the timed countdown or increase elapsed time, then update the player.
  4. Update compass, hints, toast, throttled minimap and HUD.
  5. Sample performance and adjust WebGL pixel ratio if eligible.
  6. Render WebGL or Canvas, then schedule tick again.

Three different meanings of time

ClockUsed forConsequence
Clamped frame deltaMotion, countdown, high-score elapsed time, FPS sample accumulator.Long frames and background gaps contribute at most 50 ms each.
performance.now()Hint expiry, pulses, toast, start timestamp.A hint may expire while the simulation barely advances.
Server Date.now()Run lifetime and submission plausibility.Measures real server elapsed time, independently of browser simulation.

Clamping prevents a giant movement jump after a stall, but silently slows game time below 20 FPS. A 200 ms real frame counts as only 50 ms. Therefore the countdown and high-score elapsed time do not remain wall-clock accurate under severe slowdown. Pausing on visibility changes or separating simulation delta from scoring time would make the rule clearer.

The same clamped delta contaminates the FPS estimate: at a real 10 FPS, ten frames each contribute 0.05 seconds, giving an estimate near 20 FPS. The low-resolution threshold can still trigger, but the number is not actual FPS. Measure performance using the unclamped elapsed time and reserve a capped delta for motion.

Most pulsing uses absolute time, but rings rotate by a fixed increment each frame. They spin faster on a high-refresh monitor. Proposed: express rotation as radians per second times dt, or calculate orientation from elapsed time.

15 · Systems design

Rules, difficulty and scoring

ModeImplemented rulesDesign purpose
PracticeChoose a level, no countdown or points; completing it leads to a summary rather than an endless sequence.Learn navigation and study mazes without penalty.
Timed RunAdaptive countdown, three lives on a freshly prepared level, points for level/time/lives.Pressure, mastery and retries.
High ScoreNo countdown failure; score depends on pace against the route target.Reward speed while allowing continued exploration.

Difficulty grows in area

The executable formula is N = 5 + (level - 1) × 2: side lengths 5, 7, 9, 11 and so on. A comment says four cells per level, but SIZE_INCREMENT is 2. Cell counts grow as N²: 25, 49, 81, 121. Level 20 already has a 43 × 43 grid (1,849 cells). There is no client-side global size cap.

Hints are level + 2 per level. A timed retry keeps the same maze, returns to the marked start, randomizes facing and resets the timer and hints. Lives decrement on timeout. A newly prepared next level resets lives to three, so lives are a per-level retry budget rather than a permanently shrinking run budget.

The adaptive timer

T = factor × max(1, path.length − 1) × CELL_SIZE / MOVE_SPEED

The factor is 3 for normal pointers and 4 for coarse pointers. For a 12-step route: distance is 48 units, ideal straight travel time is about 9.23 seconds, and the allowances are about 27.69 seconds and 36.92 seconds. The multiplier covers turns, acceleration, exploration and input friction; the formula does not explicitly model them. It measures centre-to-centre route length and omits the final boundary travel.

Exact score formulas

// Timed Run, per completed level
floor(220 + level × 42 + max(0, floor(timeLeft)) × 6 + lives × 110)

// High Score, per completed level
target = max(1, timerFromOptimalRoute())
elapsed = max(1, elapsedSeconds)
pace = clamp(target / elapsed, 0.25, 3)
floor(220 + level × 42 + pace × 6 × 20)

Completing level 1 with 10 whole seconds left and three lives gives 220 + 42 + 60 + 330 = 652. At high-score pace 2 on level 1, the reward is 220 + 42 + 240 = 502. The pace cap limits the maximum speed bonus to 360 points; the lower clamp still grants 30 speed points on a very slow completion.

High Score reuses the pointer-dependent target timer, so the same elapsed time can yield a different pace on coarse-pointer and desktop devices. Timed Run’s leftover-time points also favour longer allowances. Combining these results in one board is a fairness decision worth measuring, not assuming equivalent.

Continue stores only the highest reached level. It generates a new maze there, restores three lives, and estimates earlier score from 220 + level × 42 per previous level. It does not resume the original maze, exact score, time or position. Present that distinction clearly to players.

16 · Web services

Storage, APIs and trust

Local progress and scores

localStorage persists strings per origin. The game JSON-encodes progress and top-ten scores, catches read/write errors, normalizes records and caps the display at ten rows. Local data is editable by the user, so it cannot prove a competitive result. life_runner_app_version records the version check separately.

Progress is saved when a scored level is prepared, not only when completed. renderScoresInto() uses DOM nodes and textContent for aliases rather than inserting them as HTML. That preserves text as data and avoids treating a player name as markup.

The host’s score protocol

RequestRoleImportant behaviour
GET /api/labyrinth/versionReturn server version.Client compares 0.5.1, clears matching Cache Storage entries on mismatch, then changes query parameters and reloads up to twice.
GET /api/labyrinth/scoresRead global top ten.Client replaces its displayed/cached board when refresh succeeds.
POST /api/labyrinth/runsBegin scored run using mode and start level.Returns a random run token with a two-hour lifetime. Practice does not request one.
POST /api/labyrinth/scoresSubmit token, alias, score, level and mode.Validates input and plausibility, consumes the token and writes the board.

The score-read limiter allows 90 requests per minute. The write limiter is shared across run creation and score submission, allowing 20 requests per 15 minutes. POST JSON is limited to 8 KB. Rate limits constrain traffic; they do not establish that a maze was solved.

The server creates 32-byte random tokens, stores run metadata in memory, and checks mode, finite positive score, level range up to 60, minimum duration, expiry, progression frequency and a score upper bound. Alias validation restricts length and characters and rejects URLs, contact-like strings and blocked terms. Fuzzy blocked-term checking uses normalization and Levenshtein edit distance; broad substring filters can produce false positives.

These are plausibility checks, not authoritative gameplay. The server does not regenerate a recorded maze or verify the player’s trajectory. A recorded IP is not checked against the submitter in the inspected route. Server restarts lose in-memory run tokens; multiple instances would need shared session state.

Durable writes and failure paths

The host retains up to 100 positive-score records in data/labyrinth-scores.json, exposing ten. It queues read-modify-write work with a promise chain to avoid simultaneous requests overwriting one another within a single process. Writing a temporary file and renaming it reduces the risk of readers seeing partly written JSON. It is not a distributed database transaction.

If fetching/submitting fails at the network level, the client can fall back to local storage. An explicit HTTP rejection sets an error message rather than silently saving locally. A valid global score response refreshes the local cache. The current messages do not always make local/global save status sufficiently distinct.

Review point: run tokens are consumed before the file write succeeds. A disk error can leave a legitimate user unable to retry that submission. Also, once a global board is loaded, loadScores() prefers it; a local-only insert can be hidden on a subsequent render. Both are worthwhile failure-path exercises.

Loading, caching and security boundaries

The engine loader fetches same-origin script bytes, shows byte progress when Content-Length is known, decodes them with TextDecoder, then executes them with new Function. CDN sources use injected script tags because cross-origin script loading and readable fetch responses have different CORS requirements. Remote progress is simulated, not a measured byte percentage.

Executing fetched code makes that engine source a code-trust boundary. A stricter Content Security Policy may block new Function; a proposed production revision would use a pinned local script/module and an appropriate policy instead of adding permission for dynamic evaluation. The current CDN scripts have no integrity attributes. Pinning a version supports reproducibility but does not replace dependency review.

The version checker uses cache: "no-store". Deleting named Cache Storage entries does not purge all browser HTTP cache, and no service worker is implemented here. Query parameters provide cache-busting URLs; the two-reload guard prevents a persistent client/server version mismatch looping forever.

17 · Engineering budgets

Efficiency and resource budgets

Optimisation begins with a measurement and a target device. Small mazes can hide problems that dominate after many levels. CPU work includes algorithms, draw preparation, DOM updates and ray stepping; GPU work includes triangles, material/light shading, transparent overdraw and pixel count.

Adaptive graphics

detectQualityProfile() uses optional device memory/core hints and touch/screen heuristics. Lower-end profiles disable antialiasing, reduce pixel ratio and change fog density and light intensity. Touch input is not proof of a slow GPU; these are starting guesses.

Every nominal two sampled seconds, WebGL resolution drops by 0.1 below an estimated 27 FPS, or rises by 0.1 above 52 FPS, within configured limits. The gap between thresholds avoids constant oscillation. The minimum ratio is 0.85. Fix the clamped-delta measurement issue before treating these numbers as true frame rates. Resizing currently reapplies the initial device/profile ratio, potentially overriding the adaptive choice.

Resource lifetime matters

JavaScript garbage collection and GPU resource release are separate concerns. scene.remove(worldRoot) stops rendering a group; it does not explicitly dispose its buffers, materials and textures. A proposed cleanup routine should collect unique resources into sets, dispose geometries/materials once, and preserve the shared cached glow texture until the game is finished. Do not dispose a resource still referenced by the next level.

Use renderer.info.render.calls, triangle counts and renderer.info.memory during a local debugging session; combine them with a browser Performance recording. Check a fixed maze at a fixed viewport, then repeated level replacement. Improvement means a measured reduction without changed rules or broken hints.

Budget exercise: At level 20, N=43. Count 1,849 floor meshes before walls and markers. Estimate pixel cost at ratios 1 and 1.8: the latter has 3.24 times the pixels. Decide whether your bottleneck is likely draw calls or fill rate only after a profile.
18 · The player’s perspective

User experience and accessibility

A technically correct maze can still be confusing. The preview gives planning time before the clock starts. A fixed southern sun and compass reduce disorientation. Distinct start/exit markers and palette changes help identify place and level. Timeout messaging lets players understand failure before retrying the same map, preserving learning from the previous attempt.

The game’s original Taskit brief imagined spending earned tokens on help. This standalone file instead grants hints per level and resets lives during preparation; it does not call a Taskit wallet or implement token purchasing. Avoid presenting the original product concept as an existing integration.

Design choices to evaluate with players

  • Two continuation steps after a clear: success → continue → staging message → continue → preview → start creates several clicks. Test whether the pacing feels celebratory or repetitive.
  • Navigation cues: full-map hints help map readers, but colour-only cues can fail for colour-vision differences. Pair colour with shapes and text.
  • Control discovery: hidden joystick graphics and mouse capture need a clear first-use demonstration. Arrow keys strafe, which may surprise players expecting turning.
  • Failure feedback: distinguish a timeout, an API rejection, a local save and a global save. Each requires a different next action.
  • Mode expectations: “Continue” is a new maze at the saved level, Practice ends after one clear, and a timed next level restores lives.
  • Competitive fairness: input factors, random route lengths, continued-run estimates and shared mode boards affect score comparability.

Proposed accessibility work

Keep keyboard focus visible, move it into newly opened dialogs, trap it appropriately, and restore it when closing. Give overlays accessible names and dialog semantics. Announce meaningful events such as “hint used” or “life lost”, rather than streaming the timer every frame to a screen reader. Test each menu with keyboard only.

Offer remappable controls, explicit keyboard turning, mouse/touch sensitivity, adjustable field of view, reduced motion/pulsing and a high-contrast cue set. Respect reduced-motion preferences in decorative effects. Preserve zoom where possible and provide scalable HUD text. A canvas first-person maze also needs an alternative navigable representation if nonvisual play is an intended requirement; ARIA labels alone cannot make a spatial game equivalent.

There is no implemented audio or haptic system. Optional directional audio and event sounds could help feedback, but should be independently controllable and supplemented visually. Evaluate motion comfort with real players instead of treating a narrow pitch range as a complete accessibility solution.

Usability session: Ask a new player to start Practice, orient north, use a hint and explain what Continue will restore. Observe hesitation without coaching. Repeat with touch and keyboard-only menus. Record task completion, confusion and comfort, not just whether a button technically worked.
19 · Critical reading

Source review and debugging

The following findings come from static inspection of this snapshot. They distinguish intended design from executable behaviour. This tutorial documents them; it does not silently patch game rules.

1. Exit collision and completion disagree

applyWallCollisionBuffer() clamps the player to mazeHalfWorld − 0.38. The intended outward completion threshold is only 0.38 × 0.22 = 0.0836 units inside the outer edge. The player is stopped 0.2964 units before that threshold. Additionally, checkExitCross() tests any open north/south/west/east side of the exit cell instead of using exitCell.dir. An internal open side can therefore trigger completion.

Reproduce: use a small test maze with a known north exit; put the player in the exit cell, approach the boundary, and inspect position after the collision clamp. Then cross an internal open edge and watch the completion condition. Proposed correction: agree on a single exit plane and outward direction; allow only the intended exit corridor through the boundary clamp, or put a reachable finish threshold inside it. Test all four exit directions and nearby non-exit cells.

2. Client/server score bounds have different maze rules

The client uses 5 + (level−1) × 2 and speed 5.2. The server’s labyrinthLevelSize() instead returns min(15, 6 + level−1), and its timed bound uses speed 5.5. Its maze size caps at 15 while the client keeps growing. These are different assumptions; at later levels the server’s bound may reject legitimate timed scores. Derive both rules from shared versioned configuration or submit verifiable run data before claiming the validator matches the game.

3. Graphics compatibility and lifetime

r128 colour output uses the older encoding API; removed world groups lack explicit disposal; fallback setup omits desktop turning/resize wiring; loader requests lack a timeout. Verify each independently instead of grouping all failures under “WebGL is slow”.

4. Time and interaction edge cases

Clamped time changes scoring under low FPS, ring rotation depends on refresh rate, and focus loss is not an explicit paused state. Keyboard state is set on keydown and cleared on keyup; focus loss can miss keyup. Proposed blur handling should clear held input and define a consistent pause policy.

Async run creation is launched without awaiting it. If an old request resolves after a new run starts, it can overwrite run-token state. Test delayed requests and rapid run restarts; a request generation ID can reject stale responses. Practice summary text suggests entries can be saved, while the save handler returns “Practice runs are not scored”; reconcile the product wording with the actual action.

20 · Build and explain

Build-along exercises

Work in a local copy or branch. Change one system at a time. Write down a prediction, implement, then compare the observed result. The examples above are teaching fragments, not replacements for the complete game.

  1. Extract a deterministic maze core. Move cell creation and generation into pure functions accepting a random-number function. Generate two mazes with the same seed; their walls, start and exit must match.
  2. Prove the graph contract. For each neighbour pair, assert east equals west and north equals south. Flood-fill from start and require N² reachable cells. Check that the selected exit is on the boundary and not a corner.
  3. Build a tiny overhead viewer. Render a 5 × 5 maze using Canvas lines. Overlay a BFS solution. Confirm the path stays inside open passages and includes both endpoints.
  4. Repair exit semantics. Test the clamp/finish-plane interaction before changing it. Add tests for all exit directions and for walking across an internal open wall of the exit cell.
  5. Make renderer-independent controls. Move shared keyboard/look/resize wiring out of initThree. Force fallback mode and verify turning, hints, menu escape and resizing on desktop and touch.
  6. Separate real time from simulation time. Keep a motion delta cap, but choose and document whether countdown and high-score pace use active real time. Simulate a long frame and a hidden tab; assert the chosen policy.
  7. Optimise with evidence. Replace BFS shift with a head index, then profile. Next compare ordinary meshes with instanced geometry on a fixed large maze; preserve per-tile hint behaviour.
  8. Improve service resilience. Reject stale run-creation responses; distinguish local/global status; keep a legitimate submission retryable after persistence failure. Exercise each with a mocked delayed/failing server.
  9. Design a fair challenge mode. Use one seed, input policy, scoring version and starting state for a cohort. Explain which remaining client-trust problems require server authority.
  10. Teach it back. Explain to another learner how a key press becomes displacement, how a wall becomes pixels, and why the shortest-path algorithm cannot use DFS as a drop-in replacement.
Self-check: why not use the rendered meshes as the only maze data?

A compact cell graph supports generation, hints, movement and the fallback without depending on a graphics engine. Meshes are a presentation that can be rebuilt. Keeping the rules independent makes tests and alternative renderers easier.

Self-check: why doesn’t increasing emissive intensity create a shadow?

Emissive shading changes the surface’s own light-like contribution. A cast shadow requires an occlusion technique such as shadow mapping and appropriate light/mesh configuration. This package has no enabled shadow-map pipeline.

Self-check: does a run token prove a score is honest?

No. It proves possession of a server-issued session token and lets the server enforce some constraints. The inspected server still trusts client-reported progress within plausibility bounds; it does not replay the maze navigation.
